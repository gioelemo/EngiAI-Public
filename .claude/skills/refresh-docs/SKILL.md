# Refresh docs

Audit every README and every file under [docs/](../../../docs/) for drift against the current state of the codebase **and** for inconsistencies between one another. **Propose** edits — never apply them without explicit user confirmation. Docs contain hand-curated prose (tutorials, rationale, worked examples) that is more valuable than anything auto-regeneration could produce, so this skill's job is to catch *factual drift* and *cross-file contradictions*, not to rewrite prose.

This skill is the multi-file sibling of `refresh-claude-md`. The core drift-detection logic is the same; the new dimension is **consistency across files** — the same fact stated differently in two docs is a bug even if one of them is still correct.

## Process

Run these steps in order. Batch independent read/grep operations in parallel where possible.

### Step 1 — Build the docs corpus

Discover all docs-in-scope with one `Glob` pass, then filter out vendored / generated / submodule paths.

**In scope:**
- The root [README.md](../../../README.md)
- Every `README.md` under [src/](../../../src/), [benchmarks/](../../../benchmarks/), [scripts/](../../../scripts/), [services/](../../../services/)
- Everything under [docs/](../../../docs/) — `.md`, `.rst`, and any other hand-written sources under `docs/source/` (excluding `docs/build/` and auto-generated `docs/source/api/` stubs)

**Out of scope — do not read or edit:**
- `.pytest_cache/`, `.venv/`, `node_modules/`, `__pycache__/`
- `data/mmore/cache/**` (vendored model cards)
- `thesis/`, `paper/`, `paper-revision/` (git submodules — owned by other repos)
- `docs/build/` (Sphinx output)
- `docs/source/api/` if it is auto-generated by `docs/generate_api_docs.py` — verify by reading the top of any file there; if it says "auto-generated, do not edit", skip the whole directory

List the corpus back to the user before proceeding so they can veto any file.

### Step 2 — Extract verifiable claims from each file

Read each file in the corpus in full. As you read, build a per-file list of **verifiable claims**, categorized exactly as in `refresh-claude-md`:

- **Path claims** — specific files or directories
- **Command claims** — shell commands, make targets, CLI invocations, pip/docker commands
- **Environment variable claims** — env vars and their defaults
- **Symbol claims** — classes, functions, module names
- **Architectural claims** — prose describing how components relate
- **Parameter/config claims** — numeric ranges, defaults, tolerances, port numbers, URLs
- **Version claims** — Python version, package versions, model IDs (e.g., `openai:gpt-4.1`)

Ignore pure commentary, tutorials, and rationale — those aren't "facts" that can drift.

**Track provenance.** For each claim, remember which file and line it came from. You will need this in Step 4 to detect cross-file conflicts.

### Step 3 — Verify each claim against the current repo

Same table as `refresh-claude-md`:

| Claim type | How to verify |
|---|---|
| Path (file) | `Glob` for the exact path. Must exist. |
| Path (directory) | `Bash(ls -la <dir>)` or `Glob` with `**` inside it. |
| Command / make target | `Grep` in `Makefile`, `package.json`, `pyproject.toml`. |
| Environment variable | `Grep` for the var name across `src/` and config files; cross-check default against [.env.example](../../../.env.example). |
| Symbol (class/function) | `Grep` for `class <Name>` / `def <Name>`. |
| Architectural prose | Spot-check by reading the named entry file. |
| Numeric parameter | `Grep` for the constant / config key in the source file it belongs to. |
| Version claim | Check `pyproject.toml`, `requirements*.txt`, or the relevant config file. |

**Parallelize aggressively.** Dispatch all independent grep/glob verifications in a single message.

### Step 4 — Cross-file consistency pass

This is the step that makes this skill different from `refresh-claude-md`. After Step 3, you have a global list of claims. Group them by topic and compare.

**What to look for:**

- **Same command, different wording** — e.g., README.md says `pip install -e ".[dev]"` and docs/source/installation.md says `pip install -e .[dev]`. Flag even if both work, so the user can pick one canonical form.
- **Same env var, different default** — e.g., root README says `MMORE_RAG_URL=http://localhost:8000` and benchmarks/README.md says `http://localhost:8001`. One is right, one is wrong (or they describe different services and should say so).
- **Same feature described with different capabilities** — e.g., one README says "RAGAgent supports PDF and DOCX" and another says "RAGAgent supports PDF only".
- **Install / quickstart steps out of order or contradictory** between root README and docs/source/quickstart.md.
- **Model / version IDs** that drift — one file says `gpt-4o`, another says `gpt-4.1`.
- **Port numbers** — services/prusa_mcp_server/README.md vs .env.example vs docker-compose.
- **URLs and hostnames** — Euler cluster, MMORE, Prusa MCP.

**How to structure the check:** for each category of claim, build a small table of `(file:line, claim)` and eyeball for disagreement. You do not need exhaustive pairwise comparison — only claims about the *same subject* conflict.

When you find a conflict, determine the ground truth from the code (Step 3 already told you which version matches reality). The correct file wins; the others need updating.

### Step 5 — Consult recent git history for context

Run `git log --since="3 months ago" --name-only --pretty=format:"%h %s"` to see recently touched files. Any docs section describing code in a frequently-changed file is a higher suspicion target. Also run `git log --oneline -- <doc_file>` for each doc in the corpus to see when it was last touched — docs untouched for months that describe recently-refactored code are prime drift candidates.

### Step 6 — Produce the drift report

Output a single markdown report with this structure. Do **not** edit anything yet.

```
## Docs drift audit

### Corpus (N files)
Bulleted list of every file audited, grouped by directory.

### 🔴 Confirmed stale (N)
Drift against the code. For each:
- File + line range
- Quote the stale text
- Explain what's wrong (cite the source-of-truth file/line)
- Propose the exact replacement text

### 🟠 Cross-file inconsistency (N)
Same fact, different wording. For each:
- Topic (e.g., "install command", "MMORE_RAG_URL default")
- Table of `file:line → current text`
- Which one matches reality (or "both wrong")
- Propose the canonical version and the exact replacements for each divergent file

### 🟡 Suspect (N)
Claims that might be stale but need human judgment. For each: file+line, quoted text, why it's suspect, ask user to confirm.

### 🟢 Verified (N)
One-line count + category breakdown. No per-claim detail.

### ⚪ Not checked (N)
Files or sections skipped (pure tutorials, auto-generated API stubs, etc.). List briefly.

### Suggested additions (N)
New subsystems or features that exist in code but are mentioned in *no* doc. Flag only — do not draft content.
```

**Tone rules:**
- Be specific. "Stale path" is useless; `docs/source/installation.md:42 — references src/ui/components/excalidraw which was removed in af1ce9e` is useful.
- Quote with file + line numbers.
- For 🔴 and 🟠 items, write the *exact replacement text*, not just "update this."
- Keep 🟢 to a count + categories only.
- For 🟠, always identify which file is the canonical / ground-truth version so the user knows what to align to.

### Step 7 — Ask before editing

After presenting the report, stop and ask the user which items to apply. Options:

1. Apply all 🔴 items as-proposed
2. Apply all 🟠 items using the canonical version from the report
3. Apply specific items by number (mix of 🔴 and 🟠)
4. Skip editing — user will handle manually
5. Drill into a 🟡 item for deeper investigation

Only use `Edit` after the user picks items. For each edit, use the exact replacement text from the report — do not reword on the fly. When applying a 🟠 fix that touches multiple files, edit every affected file in the same round so the corpus stays consistent.

## Known drift hotspots in this repo

Seed your suspicion on the first pass with these historically-drifty areas:

- **Install commands** — root README vs docs/source/installation.md vs docs/source/quickstart.md. The canonical form lives in [Makefile](../../../Makefile) `install` target and [pyproject.toml](../../../pyproject.toml).
- **`LLM_MODEL` default** — [.env.example](../../../.env.example) is ground truth. Has drifted between `gpt-4o`, `gpt-4.1`, etc.
- **Agent list** — check [src/agents/](../../../src/agents/) against any doc that enumerates agents. Added/removed agents are a common drift source.
- **MMORE / Prusa MCP ports and URLs** — compare docs against [.env.example](../../../.env.example) and [docker-compose.yml](../../../docker-compose.yml).
- **Submodule references** — `.gitmodules` is ground truth. Several docs have historically referenced the removed `streamlit-excalidraw` submodule.
- **Prompt style lists** — [benchmarks/problems/beams2d/generate_prompts.py](../../../benchmarks/problems/beams2d/generate_prompts.py) `PROMPT_STYLES` dict is ground truth for the beams2d benchmark. The same list appears in multiple docs and tends to fall out of sync.
- **Problem registry** — [benchmarks/shared/problem_registry.py](../../../benchmarks/shared/problem_registry.py) `PROBLEMS` dict is ground truth for which problems are available in `--problem`.
- **CLAUDE.md vs docs** — if you also see drift between CLAUDE.md and a doc file, flag it as a 🟠 and suggest the user also run `/refresh-claude-md`.

## What this skill deliberately does NOT do

- Does not rewrite prose, tutorials, or rationale — those are the *value* of the docs.
- Does not apply edits without explicit per-item confirmation.
- Does not draft content for missing sections. If a new subsystem exists in code but no doc mentions it, flag under "Suggested additions" with a pointer to the relevant source files and stop.
- Does not touch auto-generated API docs under `docs/source/api/` (regenerated by `docs/generate_api_docs.py`).
- Does not touch git submodules (`thesis/`, `paper/`, `paper-revision/`) — those are owned by other repos.
- Does not touch vendored model cards under `data/mmore/cache/`.
- Does not touch [CLAUDE.md](../../../CLAUDE.md) — use `/refresh-claude-md` for that. If this skill finds that CLAUDE.md also disagrees with a doc, flag it in the report but leave the fix to the other skill.
- Does not touch memory files under `~/.claude/projects/.../memory/` — separate system.
